## 1. WP 이동 거리 불일치 — 캔버스 고정 배율 + goThroughPoses 오버슈트

**증상**

대시보드에서 웨이포인트를 클릭해 "이동"을 실행하면, 화면에서 마커가 움직이는 거리보다 실제 로봇이 움직이는 거리가 훨씬 컸다.

**진단 과정**

`waypoint_canvas.cpp`/`p6_patrol_page.cpp`를 훑어보니 캔버스 좌표 ↔ 실제 미터 환산에 서버가 내려주는 `map.resolution`(대개 0.05, 즉 20px/m)을 안 쓰고, 예전부터 쓰던 고정 배율 `kPxPerMeter=40`(즉 40px/m)을 그대로 쓰고 있었다. 실제 해상도와 배율이 2배 가까이 달라, 화면에서 클릭한 지점과 로봇이 실제로 가는 지점이 크게 어긋났다.

별개로 `careguard_nav/waypoint_manager.py`를 보니, 단일 웨이포인트 이동도 `goThroughPoses`를 쓰고 있었다 — 이건 "여러 지점을 매끄럽게 지나가는" 용도라 `goal_checker`가 `goToPose`만큼 엄격하게 정지시키지 않아, 실 로봇 테스트로 목적지를 지나쳐 더 가버리는 것을 확인했다.

**원인**

1. 캔버스가 실제 지도 해상도를 무시하고 고정 배율만 썼음.
2. 단일 목적지 이동에 부적합한 Nav2 API(`goThroughPoses`)를 썼음.

**해결**

- `canvas_geometry.cpp`에 `metersToCanvas`/`canvasToMeters`를 추가해 서버의 실제 resolution/origin으로 환산하도록 전면 수정.
- `waypoint_manager.py::_go_through`가 목적지가 하나면 `goToPose`, 여럿이면 `goThroughPoses`를 쓰도록 분기.

**교훈**: "화면에서 클릭한 자리와 실제로 가는 자리가 다르다"는 리포트는 좌표 변환 공식 자체보다, 그 공식에 들어가는 **입력값(해상도)이 진짜 서버 값인지 하드코딩된 값인지**부터 의심할 것.

## 2. "순찰 시작" 시 대시보드만 움직이고 실제 로봇은 그대로

**증상**

"순찰 시작"을 누르면 대시보드의 현재위치 마커는 경로를 따라 움직이는데, 실제 로봇은 제자리에 그대로 있었다.

**진단 과정**

`P6PatrolPage::runTestRun()`을 읽어보니 `canvas_->startTestRun(order, chargeId)`를 서버 API 호출과 무관하게 항상 먼저 호출하고 있었다. 이건 원래 "테스트 실행"(로컬 미리보기) 기능으로 만들어졌던 코드가 실제 "순찰 시작" 버튼에도 그대로 남아있던 것 — 서버에 아직 배포 안 된 경로면 그 뒤의 실제 API 호출은 조용히 `return`되는데, 화면은 이미 애니메이션이 재생 중이라 사용자는 "로봇이 순찰 중"이라고 착각하게 된다.

**원인**

`P5MapPage`의 "이동" 버튼이 예전에 겪었던 것과 같은 유형의 버그(트러블슈팅 문서 2026-09-07 8번) — 로컬 미리보기용 애니메이션 함수가 실제 기능의 자리를 대신 차지하고 있었음.

**해결**

`canvas_->startTestRun(...)` 호출을 완전히 제거. 경로가 서버에 배포 안 돼 있으면 명확한 안내 메시지를 띄우도록 변경. 이제 현재위치 마커는 로봇이 실제로 보내는 `robot_position` WS 메시지로만 움직인다. 더 이상 안 쓰는 `startTestRun`/`updateRobotAlongTestPath`/관련 타이머·시그널 코드 정리.

**교훈**: "버튼을 눌렀을 때 화면에 반응이 있다"가 "실제로 로봇까지 명령이 갔다"를 보장하지 않는다 — 특히 데모/미리보기용으로 만든 코드가 나중에 실제 버튼에 재사용되는 경우, 코드를 직접 안 읽으면 알아채기 어렵다.

## 3. WP 추가 후 웨이포인트들이 한곳에 뭉쳐 보임

**증상**

웨이포인트를 새로 추가하고 "경로 편집" 모드로 들어가 경로 이름을 입력하면, 방금 추가한 웨이포인트들이 전부 지도의 한 지점(원점 근처)으로 모여 보였다.

**진단 과정**

`WaypointCanvas::Waypoint`에는 캔버스 픽셀 좌표(`pos`)와 별개로 실제 map 프레임 미터 좌표(`metersPos`)가 있다. `metersPos`는 서버에서 불러온 웨이포인트에만 채워지고, 로컬에서 새로 추가/드래그한 웨이포인트는 "화면이 이미 떠 있는 상태에서만 만들어지니 기본값(0,0)이어도 문제없다"는 전제로 안 채워지고 있었다. 그런데 `resizeEvent`가 지도가 있는 캔버스에서는 항상 `requestMetersResync()`를 부르고, 이 함수는 **모든** 웨이포인트의 `pos`를 `metersPos` 기준으로 다시 계산한다 — "경로 편집" 모드 진입으로 우측 패널 폭이 바뀌어 캔버스가 리사이즈되면 이 경로를 다시 타면서, `metersPos`가 (0,0)인 로컬 웨이포인트들이 전부 지도의 실제 원점으로 순간이동해버렸다.

**원인**

`resizeEvent`가 리사이즈 때마다 부르는 `requestMetersResync()`가, "로컬 웨이포인트는 이 경로를 다시 안 탄다"는 애초의 전제가 깨진 상황(생성 이후에 또 리사이즈가 일어나는 경우)을 고려하지 않았음.

**해결**

`handleCanvasMoved`(드래그 이동)와 `handlePopoverSave`(새 웨이포인트 저장) 양쪽에서, `pos`가 확정될 때마다 `canvas_->canvasToMapMeters(pos)`로 `metersPos`도 같이 갱신하도록 수정. `handleCanvasMoved`는 캔버스 자신의 내부 사본에도 반영되도록 `canvas_->setWaypoints(waypoints_)`를 추가 호출.

**교훈**: "이 값은 특정 시점 이후엔 안 쓰인다"는 전제로 필드를 안 채우는 최적화는, 그 시점을 다시 타게 만드는 다른 코드 경로가 나중에 추가되는 순간 조용히 깨진다.

## 4. "매핑 취소"를 눌러도 cartographer가 안 꺼짐

**증상**

대시보드 "매핑 취소" 버튼을 눌러도 cartographer가 실제로는 계속 떠 있었다.

**진단 과정**

`downlink_node.py::_stop_slam()`을 보니 `self._slam_process`(자기 자신이 들고 있는 Popen 핸들)가 없거나 이미 죽어 있으면 "취소할 SLAM 작업이 없습니다"라고 로그만 남기고 조용히 리턴하고 있었다. 오늘처럼 매핑 도중 다운링크가 재시작된 적이 있으면 이 핸들 자체가 사라진다.

**원인**

`_ensure_navigation_running`/`_shutdown_everything`에는 이미 "핸들이 없어도 명령줄 패턴으로 찾아서 정리"하는 `_kill_external_process_group` 폴백이 있었는데, `_stop_slam`에는 이 패턴이 적용 안 돼 있었음.

**해결**

`_stop_slam`도 자기 핸들이 없으면 `_kill_external_process_group('careguard_bringup cartographer_launch.py', ...)`로 한 번 더 확인하도록 수정.

**교훈**: 같은 클래스의 문제(프로세스 소유권을 다운링크 재시작 사이에 잃어버림)에 대한 방어 코드를 한 곳에 만들었으면, 같은 프로세스를 다루는 다른 함수에도 빠짐없이 적용됐는지 점검할 것.

## 5. 방향키 텔레옵이 P5/P6 어디서도 안 먹힘

**증상**

매핑 페이지(P5), 순찰 페이지(P6) 둘 다 방향키를 눌러도 로봇이 반응하지 않았다.

**진단 과정**

두 페이지 다 생성자에서 `setFocusPolicy(Qt::StrongFocus)`를 부르고 `keyPressEvent`도 구현돼 있었다. 그런데 앱 전체에서 `setFocus()`를 부르는 곳을 찾아보니 아무 데도 없었다 — `StrongFocus`는 "포커스를 받을 자격이 있다"는 정책 설정일 뿐, 실제로 포커스를 가져오는 동작이 아니다. 페이지를 열자마자 방향키를 누르면 포커스가 사이드바 버튼 등 엉뚱한 곳에 남아있어 `keyPressEvent`까지 이벤트가 오지 않았다.

**원인**

포커스 정책만 설정하고 실제 `setFocus()` 호출이 빠져 있었음.

**해결**

두 페이지 다 `showEvent()`에서 `setFocus()`를 호출하도록 추가 — `QStackedWidget`이 페이지를 전환할 때마다 `showEvent`가 다시 불리므로, 탭을 오갈 때마다 포커스를 다시 가져온다. 캔버스 등 다른 자식 위젯들은 포커스 정책이 기본값(`NoFocus`)이라 클릭해도 페이지의 포커스를 뺏어가지 않는 것도 확인했다.

**교훈**: Qt에서 `setFocusPolicy`는 허가일 뿐 실행이 아니다 — 위젯이 실제로 키 이벤트를 받으려면 언젠가 반드시 `setFocus()`가 호출돼야 하고, 페이지 전환이 있는 UI라면 그 시점을 `showEvent`로 잡는 게 안전하다.

## 6. 지도 파일 자체의 축척(resolution) 오류 — 라이다가 벽과 안 맞음

**증상**

여러 형태로 나타났다: "wp 이동/순찰 시 로봇이 이상한 위치로 감", "rviz2에서 라이다가 지도 벽보다 작게/이상하게 잡힘", "AMCL이 비슷하게 생긴 옆방으로 착각하는 것처럼 보임". 대시보드를 거치지 않고 로봇에서 직접 rviz2로 봐도 똑같이 나타났다.

**진단 과정**

1. 서버 DB의 map 메타데이터(resolution 0.05, origin, 크기)와 로봇이 실제로 받는 `.yaml`을 대조 — 완전히 일치. 좌표 변환 공식도 표준 ROS map_server 관례와 일치. 여기까지는 문제 없음.
2. SSH로 라이다 원시 `/scan` 값을 하나 받아 확인 — 가까운 벽까지 거리값이 일관되게(2.93~2.97m) 나와서 센서 자체는 정상.
3. R-04가 쓰는 `mapd_mod2.pgm`의 출처를 추적해보니, 이번 세션의 검증된 SLAM 파이프라인(`cartographer_occupancy_grid_node -resolution 0.05`)으로 새로 뜬 게 아니라 **훨씬 이전에(2026-09-04경) 이미 만들어져 있던 파일을 그대로 가져온 것**이었다 — `resolution: 0.05`라는 값이 실측 검증된 적이 없었다.
4. 대시보드에서 실제로 줄자로 잰 구간(290cm)의 양 끝을 클릭해 좌표를 받고, (틀린) 0.05 기준으로 계산된 거리(1.83m)와 비교 → 픽셀 거리를 역산(36.6px) → 진짜 resolution = 2.90 / 36.6 ≈ **0.0792**.

**원인**

지도 이미지 자체는 정확한데(SLAM이 실제 벽 구조를 정확히 잡음), 그 이미지가 몇 미터를 나타내는지 알려주는 `resolution` 메타데이터가 검증 안 된 값이었다. Nav2의 `map_server`가 이 값을 그대로 믿고 `/map`을 뿌리기 때문에, 그 위에 겹쳐지는 실제 스케일의 라이다·오도메트리 데이터와 어긋나 보였다 — 대시보드든 rviz2든 결국 같은 `.yaml` 하나를 보는 것이므로 어느 경로로 봐도 똑같이 틀리게 나온 것.

**해결**

- `map.resolution`을 0.05 → 0.0792로 DB에서 직접 보정(같은 파일을 쓰는 R-02도 함께).
- 이 값은 서버 DB에만 반영되고, 로봇이 실제로 Nav2에 넘기는 로컬 `.yaml`은 `downlink_node.py::_download_map`이 순찰/이동 명령 때 서버 값으로 다시 만든다 — 단, `_ensure_navigation_running`은 **map_id가 바뀔 때만** Nav2를 재시작하므로, resolution만 바뀌고 map_id가 그대로면 로봇은 스스로 알아채지 못한다. 값을 바꾼 뒤에는 로봇에서 Nav2를 수동으로 한 번 재시작해야 한다.
- "파일로 등록"으로 같은 파일을 다시 올리면 그 파일의 (검증 안 된) `resolution: 0.05`로 DB가 다시 덮어써진다 — 실제로 하루에 두 번 이 문제가 재발했다. 재발 시 같은 계산으로 다시 보정.

**교훈**:
- "라이다가 지도랑 안 맞는다"는 증상은 AMCL 로직·좌표 변환 공식 이전에, **지도 파일 자체가 주장하는 축척이 실제로 검증됐는지**부터 의심할 것 — 코드가 완벽해도 입력 메타데이터가 틀리면 모든 걸 앞뒤로 어긋나 보이게 만든다.
- 실측(줄자) 기반 역산이 "코드를 더 뜯어보는 것"보다 훨씬 빠르고 확실한 진단 수단이었다.
- 이 계산은 사람이 "화면에서 크다/작다"고 말로 설명하는 것보다, 실제 좌표+실측 숫자로 다시 검증하는 게 훨씬 정확하다 — 같은 증상이 반복 보고됐을 때 "또 똑같다"는 말만으로 판단하지 말고 매번 숫자로 재확인할 것.
- SLAM으로 이 세션에서 직접 새로 뜬 지도는 검증된 파이프라인 산출물이라 이 문제에서 자유롭다 — 근본적인 해결은 파일로 가져온 예전 지도들을 전부 재-SLAM하는 것.

## 7~9. 새 지도에서 AMCL이 위치를 전혀 못 잡음 — 충전소 없음 / patrol_task 미기동 / map_id 불일치

세 가지가 연쇄적으로 나온 하나의 큰 흐름이라 묶어서 정리한다.

**증상 흐름**

1. 방금 새로 만든(웨이포인트 0개) 지도에서 "이동"을 눌러도 무반응.
2. 충전 스테이션을 등록하고 "위치 보정"까지 했는데도 여전히 무반응.
3. (별개 시점) "다시 로봇에 재빌드하고 실행했는데도" 예약된 순찰이 시간이 돼도 안 움직임 — DB엔 `status='completed'`로 남아있는데 로봇은 실제로 안 움직인 상태.

**진단 과정**

1. `GET /waypoints?map_id=`로 확인해보니 새 지도엔 웨이포인트가 0개 — 충전 스테이션이 없으면 `initial_pose_setter`가 조용히 실패하고 반환(`충전 스테이션 웨이포인트가 없습니다` 경고만 로그).
2. 충전소 등록 + 위치 보정 후에도 안 움직여서 로봇에 SSH로 들어가 `ros2 node list`를 확인 — Nav2·다운링크·업링크는 다 떠 있는데 **`patrol_task` 노드 자체가 없었다.** `_start_patrol`이 `self._patrol_client.wait_for_server(timeout_sec=2.0)`에서 실패하면 로봇 로그에만 에러를 남기고 조용히 리턴하는 구조라, 대시보드에는 아무 에러도 안 뜬다.
3. 수동으로 `CAREGUARD_MAP_ID=17 ros2 run careguard_mission patrol_task`를 켜서 임시로 풀었지만, 다음 예약 순찰에서 `patrol_run`이 `status='completed'`로 남았는데도 로봇이 실제로 안 움직인 케이스가 또 나왔다 — 이번엔 `patrol_task`가 `CAREGUARD_MAP_ID` **없이** 켜져 있었던 게 원인(충전 스테이션 캐시가 비어 복귀가 조용히 스킵됨)이었고, 별도로 `return_to_charging()`·웨이포인트 이동 루프 둘 다 Nav2 결과(TaskResult)를 전혀 확인 안 하고 있어서 실패해도 무조건 "완료"로 보고하고 있었다(8~9번 항목의 근본 원인).

**원인**

- `careguard_mission/patrol_task.py`는 `careguard_bringup`의 다른 launch 파일들과 달리 **자동으로 켜주는 코드가 없어서** 사람이 매번 SSH로 직접 실행해야 했다.
- 그마저도 `CAREGUARD_MAP_ID` 환경변수를 정확히 맞춰서 켜야 충전 스테이션 캐시가 채워지는데, 그걸 깜빡하거나 지도를 바꾼 뒤 재시작을 안 하면 캐시가 비거나 옛 지도 것으로 남는다.
- Nav2 이동 결과를 확인 안 해서, 위 두 문제(액션 서버 없음/캐시 틀림)로 인한 실패가 전부 "성공"으로 위장됨.

**해결**

- `downlink_node.py`에 `_ensure_patrol_task_running(map_id)` 추가 — `_ensure_navigation_running`과 같은 패턴으로, 다른 map_id로 떠 있으면 종료 후 정확한 `CAREGUARD_MAP_ID`로 재기동, 고아 프로세스도 정리. `_start_patrol`(이동/순찰 명령)과 `_prepare_navigation`(P6 페이지 진입) 양쪽에서 자동 호출.
- `patrol_task.py::_execute`가 각 웨이포인트 이동과 `return_to_charging()`의 `TaskResult`를 확인해, 실패하면 그 자리에서 중단하고 `status='failed'`로 정확히 보고하도록 수정.
- 새 지도엔 충전 스테이션 웨이포인트를 등록해두는 걸 표준 절차로 안내.

**교훈**:
- 로봇 쪽에서 액션 서버가 없거나 명령이 실패해도 **서버/대시보드로는 아무 신호도 안 가는** 구조라면, "대시보드에 에러가 안 뜬다"는 게 "정상 동작했다"를 보장하지 않는다 — 로봇 로그를 직접 봐야만 알 수 있는 실패가 있다는 걸 항상 염두에 둘 것.
- "매번 사람이 SSH로 미리 띄워둬야 하는 노드"는 결국 언젠가 안 띄운 채로 잊혀지고, 그 실패가 상위 계층(순찰 "완료" 상태)에 흡수돼 안 보이게 된다 — Nav2처럼 이미 자동화된 것들과 같은 패턴으로 자동 기동시키는 게 근본적인 해결책.

## 10. 웨이포인트 방향 화살표가 정반대로 그려짐

**증상**

충전 스테이션의 방향 화살표는 의도한 대로 보이는데, 나머지 웨이포인트들은 드래그로 잡은 방향과 반대로 그려지고, 실제로 로봇도 그 반대 방향을 보고 멈췄다.

**진단 과정**

1. 웨이포인트를 추가/드래그(atan2)·다이얼(YawDial)·저장(`qDegreesToRadians`)·불러오기(`qRadiansToDegrees`)·그리기(`paintEvent`) 전 구간을 추적 — 전부 같은 공식을 그대로 쓰고 있어 코드상으론 자기 자신과 항상 일치했다(캔버스 렌더링만 놓고 보면 버그가 없었음).
2. 서버에 저장된 실제 값을 직접 조회 — 충전 스테이션(WP1)의 yaw는 정확히 **0.0**(한 번도 실제로 설정된 적 없는 기본값), WP2는 약 88°(거의 위/아래 방향). 그리기 코드는 이 값을 정직하게 그리고 있어 화면 자체는 저장된 값과 일치했다.
3. 사용자가 "대시보드는 (둘 다) 똑같은 방향으로 화살표를 향하고 있고, 실제 로봇의 최종 방향만 WP1에서는 맞고 WP2에서는 반대"라고 정정 — 즉 버그는 **캔버스 렌더링이 아니라 real-world로 보내는 yaw 값** 쪽에 있다는 뜻.
4. 위치 변환(`metersToCanvas`/`canvasToMeters`)은 캔버스(Y 아래로 증가)와 map 프레임(Y 위로 증가) 사이에서 세로를 뒤집는데, **각도(yaw) 변환은 이 반전을 전혀 안 하고 있었다.** 한 축만 반사(mirror)하면 각도는 회전이 아니라 부호가 반대로 뒤집혀야 한다 — 0°/180°는 반전해도 그대로라 우연히 안 틀려 보이고, 90°/270°에 가까울수록 차이가 최대(거의 정반대)로 나타난다. 정확히 WP1(0°, 영향 없음)은 정상, WP2(88°, 영향 최대)는 반대로 나타난 것과 일치.

**원인**

캔버스↔map 프레임 좌표 변환에서 위치는 Y축 반전을 처리하면서, 방향(yaw)에는 대응하는 부호 반전이 빠져 있었음.

**해결**

`CanvasGeometry`에 `canvasYawDegToMapYawRad`/`mapYawRadToCanvasYawDeg`를 추가(각각 부호를 반전한 뒤 도-라디안 변환)하고, yaw가 캔버스↔서버 경계를 넘는 5곳(웨이포인트 저장, "이동" 전송, "위치 보정" 전송, 서버에서 불러오기, 로봇 실시간 위치 표시) 전부 이 함수를 거치도록 통일. **이미 저장된 웨이포인트의 yaw 값 자체는 옛날(버그 있는) 계산으로 저장된 것이라 재배포만으로는 안 고쳐지고, 재설정(재드래그 또는 다이얼로 재설정 후 저장)이 필요하다.**

**교훈**:
- "화면에 그려지는 게 저장된 값과 일치한다"는 렌더링 자체의 자기 일관성 검증만으로는 부족했다 — 진짜 검증은 "그 값이 실제 세계에서 의미하는 방향과 일치하는가"였다.
- 좌표계 사이에 축 하나를 반사(mirror)하는 변환이 있다면, 그 좌표계를 오가는 **각도**도 반드시 부호를 반전해야 한다는 걸 위치 변환 코드를 작성할 때부터 같이 챙겼어야 했다 — 대칭적인 각도(0°/180°)로만 테스트하면 이런 버그가 숨는다는 것도 배웠다.

## 11. 순찰 스케줄이 예약 시각에 정확히 안 켜짐

**증상**

19:40에 실행되도록 순찰 스케줄을 등록했는데, 19:41이 지나도 로봇이 움직이지 않았다. (다른 시각에도 반복 재현: 19:35 예약이 19:36까지 안 켜짐.)

**진단 과정**

`services/scheduler.py`를 보니 `_tick()`이 `POLL_INTERVAL_SEC=20`초마다 돌면서 `_is_due()`로 "지금이 트리거할 시각인지" 판정하는데, 그 판정 창도 정확히 20초(`0 <= now_sec - run_sec < POLL_INTERVAL_SEC`)였다. `_tick()` 자체가 정확히 20초 주기로 도는데, 그 20초 틱이 서버가 언제 시작됐냐에 따라 벽시계 20초 경계와 안 맞아떨어지면 run_time~run_time+20s 사이에 틱이 단 한 번도 안 걸릴 수 있다 — 이러면 그날은 영영 트리거가 안 된다. 실제로 DB의 `patrol_schedule`·`patrol_run`을 대조해보니 스케줄 자체(요일 비트마스크·활성 맵)는 전부 정상이었는데, 딱 이 타이밍 문제로 창을 놓치고 있었다.

**원인**

판정 창의 폭이 폴링 주기와 똑같아서, 폴링 타이밍이 조금만 밀려도 창을 완전히 놓칠 수 있는 구조.

**해결**

`_is_due()`가 "run_time이 오늘 안에 이미 지났는지"만 보도록 변경(상한 없이 `now_sec >= run_sec`). 같은 날 중복 실행은 이미 있던 `_tick()`의 `already_run`(그날 이미 실행됐는지 DB 조회) 체크가 계속 막아주므로 안전하다. 서버가 잠깐 멈췄다가 늦게 봐도 그날 안에는 늦게라도 한 번은 도는 게, 아예 안 도는 것보다 안전하다는 판단.

**교훈**: 폴링 기반 스케줄러에서 "판정 창"과 "폴링 주기"를 같은 값으로 두면, 두 타이머가 서로 다른 기준시점(폴링은 프로세스 시작 시각, 판정은 벽시계)으로 도는 한 반드시 놓치는 경우가 생긴다 — 판정 창은 여유 있게 넓히거나(가능하면) 아예 없애고, 중복 방지는 별도의 상태 체크(DB 등)로 하는 게 안전하다.

## 12. (기능 요청) 카메라 라이브 화면 크기·연결 끊김 표시

**증상 / 요청**

원격조종 중 화면을 보면서 로봇을 움직이는데, 카메라 화면(`CameraLiveView`)이 148×96으로 너무 작아 잘 안 보이고, 실제로 영상이 끊겨도 "LIVE" 표시가 계속 빨간불로 남아있어 끊긴 걸 못 알아챈 채 계속 조종하면 위험하다는 요청.

**진단**

`clearFrame()`(placeholder로 되돌리는 함수)이 코드베이스 어디에서도 호출되지 않고 있었다 — `setFrame()`만 계속 불려서, 새 프레임이 끊겨도 마지막 프레임이 화면에 그대로 남고 LIVE 점도 계속 빨간색이었다. 로봇의 카메라(uplink)와 이동 명령(downlink)이 서로 다른 WS 연결이라(2026-09-07 4번 항목 참고), 다운링크의 `robot_status(online)`만으로는 카메라가 실제로 끊겼는지 정확히 알 수 없다는 점도 확인.

**해결**

- `CameraLiveView`를 236×154로 확대(비율 유지).
- 다운링크 연결 상태가 아니라 **프레임이 실제로 오는지** 자체를 기준으로 판단하도록, 새 프레임마다 3초짜리 단발 타이머(`staleTimer_`)를 재시작하고, 타임아웃되면 LIVE 점을 회색으로 바꾸고 텍스트를 "연결 끊김"으로 바꾸는 `markStale()` 추가. 마지막 프레임은 그대로 남겨 뭐가 보였는지는 알 수 있게 하되, 실시간이 아니라는 걸 명확히 표시.

**교훈**: "끊기면 되돌아가야 할 UI 상태"를 만들어놓고 실제로 그 되돌리는 함수를 아무도 안 부르는 경우, 정상 동작(계속 연결돼 있는 경우)만 테스트해서는 절대 못 잡는다 — 연결이 끊기는 시나리오를 일부러 재현해보지 않으면 이런 "고장난 채로 계속 정상처럼 보이는" 버그가 특히 위험하다(이번 경우 원격조종 안전과 직결).
