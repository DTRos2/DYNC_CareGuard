## 1. "상세" 버튼에 로봇 상세 모달 신설

### 배경

사용자가 스크린샷으로 원하는 모달 디자인(로봇 코드·위치·대상자, 미니맵, 배터리·통신 지연 카드, 카메라/마이크/Nav2/웨어러블 상태 점, 진행 중 이벤트, 최근 미션, 하단 버튼들)을 제시하면서 스피커 통화·웨어러블 상태·충전 복귀를 빼달라고 요청. 순찰 취소는 클릭 5초 뒤 자동으로 충전소로 복귀하게 만들어달라는 요청도 있었음.

### 확인

- `p1_overview_page.cpp`의 "상세" 버튼(`detailBtn`)에 `connect()` 호출 자체가 없었음 — 클릭해도 아무 동작 안 하는 게 버그가 아니라 애초에 안 만들어진 상태였음.
- 실제 순찰 취소(`POST /patrol-runs/cancel`)·특정 좌표 이동(`POST /patrol-runs/drive-to-point`) API는 P6 순찰 페이지 쪽에 이미 구현돼 있어 재사용 가능했음.

### 해결

1. `pc_careguard/dashboard/src/dialogs/robot_control_modal.h/.cpp` 신규 작성 — `MiniMapView`(그 로봇의 활성 맵·웨이포인트를 가볍게 그리는 전용 위젯), 배터리/통신 지연 카드, 카메라·마이크·Nav2 상태 점(웨어러블 제외), 진행 중 이벤트 박스, 최근 미션 목록, 하단 버튼(비상정지·순찰 취소·이벤트로 이동)으로 구성.
2. "순찰 취소" 클릭 → `cancelPatrolRun()` 호출 → 성공하면 버튼에 "N초 후 충전소로 복귀" 카운트다운 표시 → 0초에 그 로봇의 활성 맵에서 `kind=='charge'` 웨이포인트를 찾아 `driveToPoint()` 호출.
3. "이벤트로 이동"은 이벤트가 없으면 비활성화만 하고 버튼 자체는 항상 보이게 함(처음엔 이벤트 없을 때 버튼을 아예 숨겼다가, "버튼이 안 보인다"는 피드백을 받고 "숨김"→"비활성화"로 수정). 색은 녹색(`Tokens::OK`)으로 지정.
4. `eventNavigationRequested` 시그널을 `P1OverviewPage` → `MainWindow`로 relay해 P2 이벤트 페이지로 전환 + `openEventByUid()`까지 이어지게 함 (`P4VideoPage::eventDetailRequested`와 동일한 기존 패턴).

**교훈**: 버튼이 화면에 있다고 그 기능이 동작한다고 가정하면 안 된다 — 이 프로젝트의 여러 페이지가 디자인 검토용 목업 단계에서 만들어져, UI는 있지만 클릭 핸들러가 없는 버튼이 여럿 있었다(P1 헤더의 "충전 복귀"/"순찰 취소"/"전체 비상정지"도 이번에 실제로 확인해보니 마찬가지였음, 2절 참고).

## 2. P1 페이지 전체를 실제 서버 데이터로 연동

### 진단 과정

1. 로봇 상세 모달에 배터리·주소·이벤트 코드 같은 실데이터를 넣으려다 보니, 애초에 이 데이터를 담고 있는 `P1OverviewPage::RobotRow`가 생성자에서 하드코딩된 배열(`rows_ = {...}`)로 채워지고 있다는 걸 확인 — R-01~R-10, 김영희·박철수 등도 전부 지어낸 값이었다.
2. KPI 카드(가동 로봇, 미처리 경보, 복약 미수령, **웨어러블 이상**, 통신 두절)도 마찬가지로 고정 문자열이었다.
3. 필드별로 실제 서버에 대응하는 데이터가 있는지 하나씩 확인:
   - 로봇 목록·온라인 여부: `GET /robots`(`ApiClient::RobotInfo`) — 있음
   - 대상자·주소·위험도(level)·복약 현황: `GET /recipients`(`ApiClient::RecipientInfo`, `medsToday`) — 있음
   - 이벤트(경보 집계·실시간 알림·로봇별 진행 중 이벤트): `GET /events`(`ApiClient::EventInfo`) — 있음
   - **배터리 %**: 로봇이 `battery_state`를 서버로 보내고는 있었지만, 서버가 그동안 대시보드로 중계를 전혀 안 하고 있었음(저배터리 자동 복귀 판단에만 내부적으로 쓰고 버림) — 이번에 서버 쪽에도 `dashboard_ws.broadcast()` 추가 필요
   - **통신 지연(ms)**: 로봇↔서버 핑퐁 지연을 재는 로직 자체가 서버에 없음 — 이번 범위에서는 만들지 않고 "-"로 표시
   - **웨어러블 이상**: 웨어러블 관련 테이블·API가 프로젝트에 전혀 없음(DB 스키마 검색으로 확인) — 완전히 새 기능 영역이라 KPI 카드 자체를 삭제
   - **복약 미수령/단계**: `medsToday`(슬롯별 done/missed/pending)로 일부 대체 가능 — "미수령 인원 수"(KPI), "오늘 done 개수"(테이블 복약 칸)로 매핑. 로봇별 "최근 미션 이력"은 대응하는 API가 없어 빈 채로 둠(지어낸 값 대신)
4. 헤더의 "충전 복귀"/"순찰 취소"/"전체 비상정지" 버튼도 확인해보니 로봇 상세 모달의 버튼들과 마찬가지로 `connect()`가 아예 없었음 — 로봇 하나를 고르는 UI가 없는 페이지 레벨 버튼이라, "그 시점에 조건에 맞는 로봇 전체"에 명령을 보내는 방식으로 구현(전체 비상정지는 진짜 모터 정지 API가 없어 `cancelPatrolRun`으로 대신함).

### 해결

- `P1OverviewPage`에 `ApiClient`·`WsClient` 멤버 추가, `GET /robots`·`GET /recipients`·`GET /events`를 각각 독립적으로 fetch해서 도착하는 대로 `rebuildRowsFromData()`로 화면을 갱신(느린 API 하나 때문에 나머지까지 안 보이는 걸 피하려고 세 요청을 기다렸다 한 번에 그리지 않음).
- `/ws/dashboard`의 `battery_state`/`robot_status`/`nav_status`를 구독해 실시간으로 반영.
- 서버(`robot_ws.py`)의 `battery_state` 분기에 `dashboard_ws.broadcast()` 추가, `dashboard_ws.py`의 신규 접속 시 hydration에도 배터리를 포함(다른 값들과 동일한 패턴).

**교훈**: "실데이터로 연동해달라"는 요청을 받으면 페이지의 필드 하나하나가 실제로 서버에 대응하는 데이터를 갖고 있는지부터 확인해야 한다 — 이번처럼 필드에 따라 상태가 다 다를 수 있다(이미 API 있음 / API는 있는데 서버가 그 값을 특정 경로로 안 흘려보내고 있었음 / 아예 이 프로젝트에 그 데이터 자체가 없음). 셋을 구분 못 하고 뭉뚱그려 진행하면, 있지도 않은 데이터를 지어내거나 반대로 이미 있는 기능(medsToday)을 놓치게 된다.

## 3. 배터리 막대·버튼 호버가 심하게 깜빡임 — UI를 너무 자주 다시 그림

### 증상

2절 작업 후 사용자가 실제 로그인해서 확인하던 중 "배터리 그래프 떨림 현상이 있다", "상세/정지 쪽에 hover 효과가 이상해 심하게 깜빡인다"고 리포트.

### 원인

`battery_state` WS 메시지가 로봇 하나에서 초당 여러 번(실측: 약 0.3~0.5초 간격) 들어오는데, 매번 `handleWsMessage()` → `rebuildRowsFromData()` → `populateTable()`을 그대로 다시 불러 로봇 테이블 전체의 셀 위젯(진행바·버튼 포함)을 매번 파괴하고 새로 만들고 있었다. 위젯이 초당 여러 번 재생성되니 마우스가 그 위에 있으면 hover 상태(enter/leave 이벤트)가 계속 끊겼다 이어졌다 하며 깜빡여 보였다.

### 해결

`QTimer batteryRefreshTimer_`(싱글샷)를 추가해, `battery_state`가 도착하면 값은 즉시 갱신하되 실제로 `rebuildRowsFromData()`를 부르는 건 타이머로 디바운스했다 — 타이머가 이미 돌고 있으면 새로 안 걸고, 1초 뒤 한 번만 다시 그린다. 값 자체는 계속 최신으로 유지되면서, 화면이 다시 그려지는 빈도만 초당 여러 번 → 최대 초당 1번으로 줄었다.

**교훈**: WS로 들어오는 값이 자주 바뀐다고 그때마다 UI를 다시 그리면 안 된다. 특히 이 코드베이스처럼 "테이블 전체를 지우고 다시 채우는" 패턴(`populateTable()`)을 쓰는 화면에서는, 갱신 빈도가 곧 위젯 재생성 빈도이므로 반드시 디바운스/쓰로틀을 걸어야 한다 — 카메라 릴레이 쪽에서 `CAMERA_SEND_INTERVAL_SEC`로 이미 같은 종류의 문제를 겪었던 것과 같은 교훈이다.

## 4. 배터리 %가 82~84% 사이를 계속 오르내림 — 값 자체가 튐

### 증상

3절 문제를 고친 뒤에도(화면이 안 떨리게 된 뒤에도) 사용자가 "지금도 84~82까지 계속 왔다갔다한다"고 지적 — 이번엔 UI 재생성 문제가 아니라 배터리 % 값 자체가 몇 초 사이에도 흔들리는 문제.

### 원인

배터리는 모터가 순간적으로 전류를 많이 끌어 쓰면 전압이 잠깐 처졌다가 돌아오는데, 그 전압을 기준으로 %를 추정하다 보니 원본 값 자체가 82→84→82%처럼 튄다. 배터리의 물리적 특성이라 로봇이 보내는 원본 신호를 "안 튀게" 만들 수는 없다.

### 진단 — 이미 해결된 사례가 있었다

사용자가 "`/home/coc/medirun` 여기서는 이미 해결했었다"고 알려줘서 그 저장소(`aurix_medirun` — 이 로봇(R-05/aurix)이 CareGuard에 통합되기 전 쓰던 원래 프로젝트)를 확인. `medirun_gui/src/services/rosbatterytelemetryprovider.cpp`에 이미 검증된 2단계 필터가 있었다:

1. **경과 시간(dt) 기반 지수이동평균(EMA)**: 고정 비율(`value += 0.2 * (new - value)`)이 아니라 `alpha = 1 - exp(-dt / tau)`(tau=5초)로 계산 — 메시지가 오는 간격이 로봇마다·상황마다 달라도(0.2초 간격이든 1초 간격이든) 필터가 "시간당 같은 정도로" 반응한다. 고정 비율로 하면 메시지가 자주 올수록 필터가 실제보다 더 둔감해지는 부작용이 있다.
2. **표시값 히스테리시스**: 필터링된 값이 현재 화면에 표시 중인 정수값에서 일정 폭(반올림 0.5 + 히스테리시스 0.75 = 1.25%p) 이상 벗어날 때만 표시 숫자를 바꾼다 — 필터를 거친 값도 반올림 경계(예: 83.4 ↔ 83.6) 근처에서는 숫자가 83↔84로 깜빡일 수 있는데, 이 히스테리시스가 그걸 막는다.

### 해결

같은 방식을 서버(`pc_careguard/server/app/ws/robot_ws.py`)에 그대로 이식했다 — `_smooth_battery_percent(robot_code, raw_percent)` 함수를 추가해 `battery_state` 분기에서 호출하고, 이미 다듬어진 정수값만 `dashboard_ws.broadcast()`로 내려보낸다.

처음엔 대시보드(`P1OverviewPage`) 쪽에서 고정 비율 EMA(alpha=0.2)로 스무딩했었는데, 사용자가 "애초에 값이 왔다갔다하는 걸 막을 수 없냐"고 물어봐서 "스무딩 위치를 서버로 옮기면 이 화면뿐 아니라 배터리를 보여줄 모든 미래의 화면이 자동으로 혜택을 본다"고 설명 후 서버 쪽으로 이전 — 대시보드는 이제 서버가 이미 다듬은 값을 그대로 저장·표시만 한다.

**현재 상태**: R-06에서 실제로 확인 — 이전엔 82~84%가 몇 초 사이에 반복해서 나타났는데, 옮긴 뒤에는 84%→83%처럼 서서히만 바뀐다.

**교훈**: 같은 로봇 하드웨어를 다루는 문제는 다른 프로젝트에서 이미 풀었을 수 있다 — 이번처럼 사용자가 "거기서는 해결했었다"고 알려주면, 그 코드를 먼저 읽고 검증된 상수(tau=5초, 히스테리시스=0.75)까지 그대로 재사용하는 게, 새로 값을 튜닝하며 재발명하는 것보다 훨씬 빠르고 안전하다. 또한 "값을 다듬는 위치"(클라이언트 vs 서버)는 사용 화면이 하나뿐일 땐 상관없어 보여도, 화면이 늘어날 걸 생각하면 단일 소스(서버)에 두는 쪽이 맞다.
